# Реализация

В главе 3 зафиксированы архитектурные и проектные решения; настоящая глава описывает, как они реализованы в работающем коде. Композиционно глава следует структуре «Реализация» курсового проекта по дисциплине ЗИС: средства, схема процесса, модули, инструменты анализа. Содержание адаптировано под две особенности проекта — наличие двух сред исполнения (GPU-симулятор и SGX-анклав через SCONE) и необходимость воспроизводимого запуска многих десятков параллельных экспериментов.

Чтобы избежать дублирования с подразделом 3.1.3, где обоснован выбор базовых средств (PyTorch, Opacus, SCONE, Flower) на уровне сравнения с альтернативами, в подразделе 4.1 излагаются только версии, особенности конкретных сборок и принципы организации двух сред. Содержательное обоснование «почему именно эти средства» даётся в 3.1.3 и здесь не повторяется.

## Выбор средств реализации

### Две среды

Реализация поддерживает две независимые среды.

— *GPU-стенд*. Linux под WSL2 (Windows-хост), Python 3.12, видеокарта NVIDIA RTX 5070Ti на микроархитектуре Blackwell (sm_120). Назначение — все ML-эксперименты главы 5: матрица атак × защит, чувствительность, MIA, GIA. Здесь же разрабатываются и отлаживаются модули `core/` и `experiments/`. На одну видеокарту параллельно запускается до шести независимых процессов через `experiments/run_parallel.py` (ограничение `--max_parallel=6` подобрано эмпирически по балансу пропускной способности и стабильности).

— *SCONE-стенд*. Docker-контейнер на базе `python:3.11-slim-bookworm` (glibc 2.36, совместим со SCONE), CPU. В режиме SIM запускается локально на любом Linux-хосте для функциональной проверки без аппаратной защиты; в режиме HW — на виртуальной машине Azure DCsv3 (Intel Xeon с поддержкой SGX). Назначение — демонстрация исполнения серверной части в TEE и измерение накладных расходов (раздел 5.6).

Разделение оправдано двумя ограничениями. Первое: SCONE привязан к Python 3.11 (совместимость с CAS-runtime платформы), а часть свежих сборок PyTorch под SGX недоступны или не сертифицированы. Второе: для GPU-стенда требуется PyTorch nightly с поддержкой sm_120, которого на момент работы нет в стабильных релизах. Совмещать обе несовместимые сборки в одном окружении нежелательно — рассинхронизация версий частая причина незаметных расхождений между средой разработки и средой исполнения.

### Управление зависимостями

Зависимости разнесены по двум файлам в каталоге `requirements/`.

| Файл | Назначение | Ключевые версии |
|---|---|---|
| `gpu.txt` | GPU-стенд | `torch>=2.12.0.dev0`, `torchvision>=0.22.0.dev0` (nightly cu128), `opacus==1.5.2`, `flwr==1.13.1` |
| `scone.txt` | SCONE-стенд | `torch==2.5.1+cpu`, `torchvision==0.20.1+cpu`, `opacus==1.5.2`, `flwr==1.13.1` |

Версии Opacus и Flower совпадают в обоих окружениях — это сделано сознательно: код модулей `core/` device-agnostic, функции пишутся через `tensor.to(device)`, без явных вызовов `.cuda()`, и должен исполняться без модификаций в любом окружении. Разница касается только бэкенда PyTorch (CUDA или CPU) и видимости sm_120.

Параметры потоковой конкуренции зафиксированы переменными окружения. Для GPU-стенда `OMP_NUM_THREADS = MKL_NUM_THREADS = OPENBLAS_NUM_THREADS = NUMEXPR_NUM_THREADS = 2`; это ограничивает контеншн между шестью одновременными процессами и даёт стабильное общее ускорение по сравнению с автодетекцией. В SCONE-стенде те же переменные равны единице — внутри анклава лишние потоки приводят к контеншну на ограниченной EPC-памяти.

### Воспроизводимость

Воспроизводимость экспериментов поддержана тремя средствами. Во-первых, в каждом запуске фиксируется случайный seed на трёх уровнях: `torch.manual_seed`, `numpy.random.default_rng(seed)` и зернование разбиения Dirichlet (`dirichlet_split(seed=...)` в `core/data.py`). Во-вторых, аппаратная конфигурация GPU-стенда зафиксирована и единственная разница между запусками одной конфигурации — недетерминированные CUDA-ядра (cuDNN benchmark включён ради скорости, фактическая девиация по итоговой ТОЗ не превышает $10^{-3}$, что для целей работы пренебрежимо). В-третьих, конфигурации экспериментов оформлены в YAML (директория `experiments/configs/`) и не редактируются по месту — повторный запуск той же конфигурации даёт сопоставимые числа.

## Описание схемы процесса обучения

Схема процесса описывает, как одна YAML-конфигурация превращается в законченный FL-сеанс. Различаются два уровня: жизненный цикл одного раунда (внутри класса `FLSimulator`) и оркестрация многих параллельных запусков (через `run_parallel.py` и пакетные shell-скрипты).

### Жизненный цикл одного раунда

Один раунд обучения $t$ выполняется в методах класса `FLSimulator` (`experiments/fl_simulator.py`, около 640 строк). Последовательность операций соответствует декомпозиции функции A5 из подраздела 2.1.

1. *Выборка клиентов раунда*. Из $N$ клиентов случайным образом выбирается активный набор размера `clients_per_round` (для межустройственного сценария — 40 из 200, для межорганизационного — 40 из 50). Вредоносные клиенты в работе размещены в детерминированных позициях (последние `m_real` индексов), что упрощает воспроизводимый анализ результатов.
2. *Локальное обучение*. Каждый активный клиент $k$ выполняет SGD-цикл из `local_epochs` эпох на собственном `DataLoader` ($E = 5$ для CD, $E = 1$ для CS — по сути FedSGD). В межорганизационном сценарии локальное обучение проходит через `Opacus.PrivacyEngine` с per-sample clipping ($R = 1{,}0$) — реализация политики П3 на уровне записей. В межустройственном сценарии используется обычный SGD без Opacus.
3. *Получение обновлений*. Возвращаются плоские тензоры $\Delta_k = w_{\text{local}} - w_{\text{global}}$ (`weights_to_flat` из `core/models.py`) и состояния буферов (BatchNorm, momentum), хранящиеся отдельно от градиентных параметров.
4. *Применение атаки*. Если активный клиент входит в множество вредоносных, его обновление подменяется одной из функций `core/attacks.py`: `alie_attack`, `ipm_attack`, `minmax_attack`, `backdoor_model_replacement`, `random_label_flip_attack` (в случае атаки на метки подмена выполнена ещё на этапе 2 через датасет-обёртку `LabelFlipDataset` или `RandomLabelFlipDataset`). ALIE и Min-Max адаптивны — используют статистику честных обновлений, известную атакующему.
5. *Адаптивный клиппинг*. Серверная функция `adaptive_clip` (`core/dp.py`) вычисляет порог $S = \min(\text{median}(\|\Delta_k\|), S_{\max})$ и обрезает каждое обновление $\Delta_k \to \Delta_k \cdot \min(1, S / \|\Delta_k\|)$. Это политика П2 с потолком $S_{\max} = 2{,}0$.
6. *Робастная агрегация*. Функция `aggregate(method, ...)` диспетчеризует на `fedavg`, `multi_krum`, `trimmed_mean`, `median` или экземпляр класса `FedRoLA` (политика П1). FedRoLA — единственный stateful-агрегатор: репутация клиентов $(\alpha_k, \beta_k)$ и история выбранных слоёв сохраняются между раундами.
7. *Шум ДП*. При `use_dp=true` и `dp_mode=central` к агрегату добавляется $\mathcal{N}(0, \sigma^2 \cdot (S/f_{\text{eff}})^2 \cdot I)$, где $f_{\text{eff}}$ — эффективное число клиентов после взвешивания FedRoLA. Параметр $\sigma$ вычислен на этапе инициализации функцией `compute_sigma` (RDP-accountant Opacus). При `dp_mode=local` шум добавляется на стороне клиента до отправки. Это политика П3.
8. *Обновление глобальной модели*. $w_{t+1} = w_t + \Delta_{\text{private}}$, состояния буферов восстанавливаются из подмножества клиентов раунда.
9. *Запись метрик раунда*. На каждом раунде собираются: ТОЗ, ТЗА (для backdoor), TPR/FPR детектора (для FedRoLA и Multi-Krum), порог $S$, использованный $\sigma$, израсходованный $\varepsilon_{\text{used}}$, статистики FedRoLA (число обнаруженных, $f_{\text{eff}}$, диапазон scores). Дамп — в CSV (`<name>_seed{N}.csv`) и JSON-сводки (`<name>_summary.json`).

Полный сеанс обучения — это $T$ повторений шагов 1–9. Целевые эксперименты используют $T = 200$, длинногоризонтные пробы — $T = 500$ (раздел 5.4.5).

### Оркестрация запусков

Скрипт `experiments/run_experiment.py` обрабатывает один процесс: читает YAML-конфигурацию, применяет переопределения вида `--override key=value`, конструирует `FLConfig` и запускает `FLSimulator.run()`. Скрипт `experiments/run_parallel.py` управляет несколькими процессами: разворачивает sweep одним из трёх способов (`--override`, `--override_grid` для декартова произведения, `--sweep` для явного списка точек конфигурации), запускает до `--max_parallel` процессов одновременно через `subprocess.Popen`, по завершении собирает per-seed CSV в общую сводку через функцию `_aggregate_per_seed_results` (усреднение по последним пяти раундам, константа `TAIL_ROUNDS = 5`).

Поверх обоих скриптов лежат пакетные shell-сценарии для конкретных серий экспериментов: `phase2_diagnostics.sh`, `phase3_sensitivity.sh`, `phase5b_mia_n10.sh`, `phase6_tomorrow.sh`, `phase6c_n20.sh` и другие. Каждый сценарий фиксирует план серии (`set -e`, общие переменные `SEEDS`, `MAX_P`, последовательные секции с метками `date` для тайминга) и пишет общий лог в `results/<phase>.log`. Это даёт две вещи. Первая: одна команда `nohup bash experiments/phase{N}.sh > results/<phase>.log 2>&1` запускает многочасовой пакет с возможностью отслеживать прогресс через `tail -f`. Вторая: тот же скрипт в репозитории фиксирует ровно тот эксперимент, который потом цитируется в главе 5 — никаких «забытых» командных строк в истории shell-а.

Артефакты экспериментов организованы по сценариям: `results/cross_device/`, `results/cross_silo/` и тематические подкаталоги (`results/mia_cd_n10/`, `results/mia_cd_n20/`, `results/local_dp_cd/`, `results/thesis5_neg/` и др.). Архив итерации 1 (333 запуска с устаревшим набором атак и защит) лежит в `results/archived_iteration1/` и в текущей работе используется только для исторической ссылки.

## Структура и функционал программных модулей

Кодовая база организована в четыре верхних каталога: `core/` — device-agnostic библиотека, `experiments/` — стенды и оркестрация, `scone/` — SGX-развёртывание, `analysis/` — постобработка. Дополнительно есть `requirements/` (зависимости двух сред) и `docs/` (исходники ВКР). Общий объём — около 4170 строк Python без учёта YAML-конфигов и shell-сценариев.

### Каталог core/

Шесть модулей, реализующих device-agnostic компоненты. Все функции принимают и возвращают `torch.Tensor` либо стандартные структуры, явных привязок к CUDA нет.

— `models.py` (~225 строк). Шесть архитектур CNN: `MicroMNIST` ($d = 4266$, основная для CD), `SVHNCNN` ($d = 89834$, основная для CS), а также `MiniMNIST`, `TinyMNIST`, `FashionMNISTCNN`, `CIFAR10CNN` для исторических и вспомогательных запусков. Утилиты: `get_model(dataset, model_name)` — единая точка выбора, чтобы не плодить условную логику в стендах; `weights_to_flat`, `flat_to_weights` — преобразование между списком тензоров и плоским вектором (нужно для линейной алгебры в робастных агрегаторах); `count_parameters`.

— `data.py` (~150 строк). Загрузка четырёх датасетов (MNIST, Fashion-MNIST, SVHN, CIFAR-10) через `torchvision.datasets` с предзаписанными mean/std для нормализации. Функция `dirichlet_split(dataset, n_clients, alpha, seed)` — детерминированное Dirichlet-разбиение для non-IID; `get_test_dataloader`, `get_client_dataloader` — обёртки `DataLoader`.

— `aggregation.py` (~335 строк). Пять алгоритмов: `fedavg`, `multi_krum`, `trimmed_mean`, `median`, плюс класс `FedRoLA` для FedRoLA-PCSI [12]. Все возвращают тип `AggResult(update, selected)`, что унифицирует обработку. Внутри `FedRoLA` — выбор слоёв пропорционально репутации, послойный косинусный анализ, мягкая фильтрация и обновление $\alpha_k/\beta_k$. Диспетчер `aggregate(method, ...)` вызывается из стендов.

— `dp.py` (~210 строк). Функции `clip_update`, `adaptive_clip` для клиппинга норм; `add_dp_noise`, `add_gaussian_noise`, `add_gaussian_noise_fedavg` для шума на сервере; `compute_sensitivity_client`, `compute_sensitivity_record` — расчёт чувствительности по сценарию; `compute_sigma`, `compute_sigma_opacus` — калибровка $\sigma$ под целевые $(\varepsilon, \delta, T, q)$ через RDP-accountant. Функция `compute_epsilon_spent` даёт обратную операцию: фактический $\varepsilon_{\text{used}}$ по итогу обучения. Класс `DPConfig` агрегирует параметры в одну структуру.

— `attacks.py` (~425 строк). Шесть атак: `random_label_flip_attack` через датасет-обёртки `LabelFlipDataset` и `RandomLabelFlipDataset`; `alie_attack` с расчётом $z$ через `compute_alie_z_max` по формуле из [2]; `ipm_attack` ($V_{\text{mal}} = -\varepsilon \cdot \mu_{\text{honest}}$); `fang_attack` (бинарный поиск по $\lambda$ против Multi-Krum, [4]); `minmax_attack` (бинарный поиск по distance-критерию); `backdoor_model_replacement` — атака замены модели [5] с предварительным локальным обучением `train_backdoor_client` на отравленном датасете `BackdoorDataset` (триггер — белый квадрат $5 \times 5$ в правом нижнем углу).

— `metrics.py` (~170 строк). `compute_mta` — ТОЗ; `compute_asr` — ТЗА на triggered-выборке; `compute_per_class_accuracy` для матрицы ошибок; `compute_label_flip_metrics` для целевой подмены меток; `compute_tpr_fpr` для оценки робастного фильтра по золотому множеству вредоносных индексов. Класс `RoundMetrics` накапливает раундовые записи и сбрасывает в CSV.

### Каталог experiments/

Стенды и оркестрация. Здесь хранятся именно сценарии запусков, а не библиотечный код.

— `fl_simulator.py` (~640 строк). Главный модуль. `FLConfig` — `@dataclass` с примерно сорока полями (FL-параметры, агрегация, ДП, атаки, расписание lr, логирование). `FLSimulator` — методы `__init__` (инициализация модели, разбиение данных, расчёт $\sigma$ и $f$ для Multi-Krum, инициализация `FedRoLA`), `_train_client` (стандартное обучение), `_train_client_dpsgd` (через Opacus PrivacyEngine для record-level DP), `_round` (один раунд по схеме выше), `run` (полный сеанс из $T$ раундов с логированием каждые `log_every`).

— `run_experiment.py` (~120 строк). Точка входа для одного запуска. Поддерживает `--override key=value` для переопределения полей `FLConfig` без изменения YAML — это и есть основной способ варьировать параметры в shell-сценариях.

— `run_parallel.py` (~210 строк). Точка входа для пакетных запусков. Реализует три режима задания вариаций (см. подраздел 4.2 выше). Запускает процессы через `subprocess.Popen`, ограничивает одновременность по `--max_parallel`. После всех запусков агрегирует per-seed результаты в общую сводку (mean ± std по последним пяти раундам).

— `mia.py` (~435 строк). Стенд для MIA-эксперимента. Поддерживает три режима: `--centralized` (одна модель, обученная стандартным SGD на всём датасете, как верхняя оценка сигнала членства), `--no_dp_only` (FL без ДП), и обычный режим со списком $\varepsilon$. Реализует loss-based и confidence-based атаки на принадлежность, а также вариант с per-class threshold (`per_class_threshold_auc`). Обучение моделей выполняется через тот же `FLSimulator` с `m_real = 0`, `attack = none`.

— `gia.py` (~230 строк). Стенд для GIA-эксперимента (атака восстановления по градиентам, реализована как DLG [6] / iDLG-вариант [8]). Применяет `dlg_attack` к одиночным образцам, варьирует уровень шума (`noise_levels`) для построения зависимости качества реконструкции от $\sigma$.

— shell-сценарии (`phase*.sh`, `run_*.sh`). Пакетные сценарии — обсуждены выше. Скрипты намеренно избыточно подробны (повторение параметров, метки `date`), чтобы лог в `results/*.log` был самодостаточным для аудита.

### Каталог scone/

Развёртывание серверной части в SGX-анклаве через SCONE. Содержит четыре основных файла.

— `server.py` (~200 строк). Flower-стратегия `KrumDPStrategy`, реализующая клиппинг + Multi-Krum + центральный шум ДП. Отличается от GPU-стенда тем, что выполняется в реальной сетевой обстановке, а не в симуляторе: принимает обновления от клиентов через Flower-RPC, агрегирует, рассылает обратно. Внутри использует те же функции `core/dp.py` (`adaptive_clip`, `add_gaussian_noise`, `compute_sigma`) и `core/aggregation.py`, что и GPU-симулятор. Это и есть прикладной смысл device-agnostic кода: алгоритм агрегации не переписывается под анклав.

— `client.py` (~155 строк). Flower-клиент `FLClient`. Локально обучает MicroMNIST или SVHNCNN, возвращает обновление через Flower-RPC.

— `Dockerfile`. Базовый образ `python:3.11-slim-bookworm`, установка `requirements/scone.txt`, копирование каталогов `core/`, `scone/`, `experiments/`, фиксация `OMP/MKL_NUM_THREADS=1`. По умолчанию запускается сервер.

— `scone_build.sh`. Сборка обычного Docker-образа, его сконификация через `scone sconify` (опции `--heap 512m`, `--dlopen 1`, флаг `--mode SIM/HW`), извлечение MRENCLAVE для последующей политики аттестации (выходной файл `scone/attestation/mrenclave.txt`). MRENCLAVE — хеш кода и данных анклава, основа политики C5 из подраздела 2.1.

В работе SCONE-часть используется как доказательство применимости (раздел 5.6 — измерение overhead) и не используется в основной массе ML-экспериментов. Это сознательное разделение ответственности: GPU-симулятор — для статистически значимых ML-измерений (десятки конфигураций × несколько seeds), SCONE-стенд — для демонстрации, что та же логика исполняется в TEE без модификаций кода.

## Средства анализа и визуализации

Постобработка результатов выполняется в каталоге `analysis/`.

— `plots.py` (~215 строк). Сводные графики. Функции `load_results` (склейка CSV из директории), `plot_convergence` (кривые ТОЗ по раундам с полосой $\pm \sigma$), функции для тепловых карт «атака × защита» и trade-off-графиков «приватность–точность». Стиль вынесен в словарь `STYLE` (DPI, толщина линий, прозрачность сетки), что обеспечивает единообразие рисунков главы 5.

— `tables.py` (~190 строк). Генерация LaTeX-таблиц. Функция `summarize_last_round(df, groupby=...)` усредняет метрики по seeds для последнего раунда; `format_mean_std` — форматирование «среднее ± std» с опциональным выделением лучшего значения жирным.

— `snr_vs_mta.py` (~175 строк). Специализированный график «SNR на раунд → итоговая ТОЗ» для подраздела 5.4.2 (S-кривые). Реализует расчёт $\text{SNR} = n_{\text{averaged}} / (\sigma \sqrt{d})$ и привязку рабочей границы $\text{SNR} > 0{,}19$ как вертикальной отметки на графике.

— `plot_gia.py` (~85 строк). Визуализация результатов GIA: исходные изображения, реконструкции при разных уровнях $\sigma$, итоговая зависимость качества реконструкции от $\sigma$.

— `notebooks/`. Jupyter-блокноты для интерактивного исследования. Финальные числа и рисунки строятся скриптами выше, чтобы запуск был воспроизводимым; блокноты служат промежуточным средством на этапе анализа.

Во всех модулях анализа фиксированы DPI и шрифты, единая палитра атак и защит (`ATTACK_LABELS`, `DEFENSE_LABELS`) — это даёт единообразный визуальный язык по всей главе 5.

## Выводы по четвёртой главе

Реализация воплощает архитектурные решения главы 3 в работающий код. Получены три основных результата.

Кодовая база организована в три верхних каталога: `core/` — device-agnostic библиотека на ~1500 строк (модели, данные, агрегация, ДП, атаки, метрики); `experiments/` — стенды и оркестрация на ~1700 строк (главный класс `FLSimulator`, скрипты `run_experiment.py`, `run_parallel.py`, `mia.py`, `gia.py`, пакетные shell-сценарии); `scone/` — SGX-развёртывание через Flower и SCONE (Dockerfile + сборочный скрипт + Flower-стратегия и клиент). Деление кода на стенды и общую библиотеку обеспечивает прямой перенос алгоритмов из GPU-симулятора в SGX-анклав без модификаций.

Поддерживаются две независимые среды разработки. GPU-стенд (Python 3.12, PyTorch nightly cu128, RTX 5070Ti) обеспечивает скорость, нужную для серий по сотне-двести запусков; SCONE-стенд (Python 3.11, PyTorch 2.5.1+cpu, образ под `python:3.11-slim-bookworm`) — для демонстрации применимости TEE и измерения накладных расходов. Между ними согласованы версии Opacus и Flower; код `core/` device-agnostic.

Жизненный цикл одного раунда соответствует декомпозиции функции A5 из подраздела 2.1 (выборка клиентов → локальное обучение → атака → клиппинг → робастная агрегация → шум ДП → обновление модели → запись метрик); оркестрация многих запусков выполнена через `run_parallel.py` и пакетные shell-сценарии, каждый из которых самодостаточно фиксирует серию экспериментов в репозитории. Постобработка организована в каталоге `analysis/` (графики, LaTeX-таблицы, специализированные срезы), что даёт единый визуальный язык для главы 5.

Стенды реализованы и проверены на эксплуатационных нагрузках — сотни запусков, многочасовые серии, общий объём сохранённых результатов покрывает все эксперименты главы 5. Глава 5 переходит к экспериментальной верификации заявленных целей безопасности (ЦБ1–ЦБ4) на этих стендах.
